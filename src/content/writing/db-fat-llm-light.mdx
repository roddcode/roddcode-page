A patient asked to book an appointment. The LLM, eager to help, started confirming — name, service, time. What it didn't check was whether this was a returning patient or someone new. Without identity validation, the system booked a slot under a name that didn't exist in the database.

I described a related failure involving a missing `doctorId` in [Deterministic AI](/writing/deterministic-ai). Both came from the same permission boundary: the LLM could write to the database without structural guardrails, and it could confirm an operation before the system validated it.

---

## The model cannot be the source of truth

An LLM can produce a plausible confirmation without checking the booking data. For this system, each confirmation has to map to a database row, a calendar event, and a scheduled reminder.

A prompt can ask the model to verify identity and availability. I also needed the application to enforce those checks, so the model could not execute a booking before the required steps were complete.

---

## DB-Fat, LLM-Light

**The LLM reasons, the database decides.**

The model receives only the tools it needs at each step of the flow. During identity verification, it has no access to booking tools. During booking, it can't modify prices. The database holds atomic locks that prevent two confirmations from landing on the same slot.

The LLM works like an employee with read-only access. It can suggest, recommend, and explain; it can't write to the database without passing through a gate that validates the operation against the system's current state.

Every state transition flows through a function that checks both the transition rules and the current database state:

```typescript
type ConversationState =
  | "idle"
  | "identity_check"
  | "service_selection"
  | "availability_query"
  | "booking_confirmation"
  | "payment_pending";

const VALID_TRANSITIONS: Record<ConversationState, ConversationState[]> = {
  idle: ["identity_check"],
  identity_check: ["service_selection"],
  service_selection: ["availability_query"],
  availability_query: ["booking_confirmation"],
  booking_confirmation: ["payment_pending", "idle"],
  payment_pending: ["idle"],
};

function transition(current: ConversationState, next: ConversationState): ConversationState {
  if (!VALID_TRANSITIONS[current].includes(next)) {
    throw new Error(`Invalid transition: ${current} → ${next}`);
  }
  return next;
}
```

The LLM operates inside one state at a time. It cannot see tools from other states. It cannot transition itself.

I applied this separation in SoffIA, a WhatsApp booking product used at a clinic in 2026. The model interpreted requests; the backend checked scheduling rules before saving bookings. The [case study](/en/work/soffia) describes the implementation and the clinic's historical results.

## The four principles

### 1. Read-only access for the model

The LLM never writes to the database. It suggests an operation; the system validates it against current state and executes only if the conditions are met.

During identity verification, the model can call `lookup_patient` and `register_new_patient`. It cannot call `book_appointment`, because that tool is not in this state's tool set at all.

In practice, this is enforced with progressive tool gating:

```typescript
const result = await generateText({
  model,
  messages,
  experimental_prepareStep: async ({ toolResults }) => {
    const currentState = await getConversationState(patientId);
    return {
      tools: TOOLS_BY_STATE[currentState],
      system: buildSystemPrompt(currentState, clinicConfig),
    };
  },
});
```

### 2. Validate in the database, not in the prompt

Whether the slot exists is something the database knows and the model does not. The model shouldn't be asked to have an opinion about it.

State transitions run inside a PostgreSQL function that encapsulates both the FSM logic and the business rules:

```sql
CREATE OR REPLACE FUNCTION advance_gate(
  p_conversation_id UUID,
  p_from_state TEXT,
  p_to_state TEXT
) RETURNS JSONB
LANGUAGE plpgsql
AS $$
DECLARE
  v_current_state TEXT;
  v_result JSONB;
BEGIN
  SELECT current_state INTO v_current_state
  FROM conversations
  WHERE id = p_conversation_id
  FOR UPDATE;

  IF v_current_state IS NULL THEN
    RETURN jsonb_build_object('ok', false, 'reason', 'conversation_not_found');
  END IF;

  IF v_current_state != p_from_state THEN
    RETURN jsonb_build_object('ok', false, 'reason', 'stale_state');
  END IF;

  IF NOT EXISTS (
    SELECT 1 FROM valid_transitions
    WHERE from_state = p_from_state AND to_state = p_to_state
  ) THEN
    RETURN jsonb_build_object('ok', false, 'reason', 'invalid_transition');
  END IF;

  UPDATE conversations
  SET current_state = p_to_state, updated_at = NOW()
  WHERE id = p_conversation_id;

  RETURN jsonb_build_object('ok', true, 'state', p_to_state);
END;
$$;
```

`FOR UPDATE` locks the row. If two concurrent requests try to transition the same conversation, one waits and gets the fresh state. Atomic validation is more reliable than any instruction you can give the model.

### 3. Tool argument validation

Tool gating already limits which tools exist at each step: no booking during patient identification, no price changes during payment. The arguments those tools receive need the same treatment.

Tool schemas are validated with Zod before execution. If the model calls `book_appointment` with a malformed date, a missing doctor ID, or a service that doesn't exist in the clinic's catalog, the SDK throws before `execute` is called:

```typescript
const bookAppointmentSchema = z.object({
  patientId: z.string().uuid(),
  doctorId: z.string().uuid(),
  serviceId: z.string().uuid(),
  startTime: z.string().datetime({ offset: true }),
  durationMinutes: z.number().int().min(15).max(180),
  notes: z.string().max(500).optional(),
});

const bookAppointment = tool({
  description: "Book a confirmed appointment slot",
  parameters: bookAppointmentSchema,
  execute: async (params) => {
    return await createAppointment(params);
  },
});
```

A tool the model cannot see is a tool it cannot call, whatever the prompt says.

### 4. Loop Shield against cognitive cycles

LLMs tend to repeat tool-calling patterns in long contexts or under uncertainty. The Loop Shield detects this repetition and forces a transition to a safe state:

```typescript
// LOOP SHIELD: From Step 4 onward, if tools appear in two consecutive
// steps, it's a cognitive loop. Tracks tool presence, not identity.
if (stepNumber >= 4) {
  const prevStepHadTools = (steps[stepNumber - 1]?.toolCalls?.length ?? 0) > 0;
  const prevPrevStepHadTools = (steps[stepNumber - 2]?.toolCalls?.length ?? 0) > 0;
  if (prevStepHadTools && prevPrevStepHadTools) {
    return { toolChoice: 'none' };
  }
}
```

It's the equivalent of a circuit breaker, but for the model's reasoning.

## What the architecture enforces

The checks sit around the model, not inside it. The database is the source of truth for every decision, the model works inside explicit constraints, and every critical operation has an atomic lock or a server-side validation behind it. When the model proposes something the database did not confirm, nothing is written.
